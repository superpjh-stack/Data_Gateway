# DECISIONS

## D-001 포트 배정은 metaprompt 4.2 표를 따른다
- 맥락: spec 11장 예시는 PLC 5020/5021과 SAN 포트 표기가 겹칠 여지가 있음
- 결정: RTU 버스 M1/M2/S1 = 7001/7002/7003, SCALE 7010, SAN 5031, FILL 5032, STUFF 5033, OPC-UA 4840, PLC Master/Slave 5020/5021, MES 8000
- 근거: metaprompt 4.2 / 영향: `config/runtime.yaml`에서 일괄 관리. 테스트는 빈 포트로 오버라이드

## D-002 Modbus 프로토콜은 직접 구현하고 pymodbus는 상호운용 검증에 쓴다
- 맥락: 고장 주입(CRC 손상, 무응답, 지연), 버스 반이중, FC 03/04만 허용하는 PLC 서버를 세밀하게 제어해야 함. pymodbus 3.15 서버는 이 훅이 제한적
- 결정: `twin.common.modbus`에 CRC16, RTU/MBAP 프레임, FC 03/04 처리, 예외 응답을 직접 구현. pymodbus 클라이언트로 PLC 서버를 읽고 쓰는 테스트로 표준 준수를 검증
- 근거: metaprompt 13장 "라이브러리로 안 되면 최소 구현" / 영향: 외부 의존 감소, 테스트로 규격 보증

## D-003 한 프로세스, 실제 소켓
- 맥락: 계층 간 경로가 진짜 프로토콜을 타야 트윈 의미가 있음. 반면 운영은 단순해야 함
- 결정: supervisor가 field·plc·edge·mes를 하나의 asyncio 루프에서 띄우되, 계층 사이는 모두 127.0.0.1 TCP 소켓(RTU over TCP, Modbus TCP, OPC-UA, HTTP)으로 통신
- 영향: `make run` 한 번으로 기동. 계층을 따로 띄우는 것은 v0.2 과제

## D-004 수용 테스트는 설정 오버라이드로 시간을 줄인다
- 맥락: AC-05(1분), AC-06(5분), AC-09(10분)을 실시간으로 돌리면 테스트가 10분을 넘음. 전역 time_scale은 폴링·타임아웃과 얽혀 불안정
- 결정: 테스트에서 `ccp_std` hold_sec, 장비 poll_ms, 고장 지속시간을 짧게 오버라이드. 판정 로직(“지속시간 전에는 알람 없음, 지난 뒤 알람”)은 그대로 검증. `runtime.time_scale`은 공정 모델의 변화 속도에만 적용
- 영향: TEST_REPORT에 테스트용 값 명시

## D-005 Edge 버퍼 단위는 "샘플"
- 맥락: 한 장비의 한 번 수집(예: 온도+습도)이 배치 경계에서 쪼개지면 MES 분배 시 한 행을 만들 수 없음
- 결정: 버퍼 한 행 = 한 샘플(항목 여러 개, 항목마다 msg_id). 배치 최대 500 항목은 샘플 단위로 채움
- 영향: `IF_SENSOR_RAW`는 항목 단위 행 그대로, 분배는 (설비, COLLECT_DT) 그룹 단위

## D-006 트윈 전용 알람 테이블 `TWIN_ALARM`
- 맥락: TD5에는 공정별 ALARM_YN과 AGE_ENV_ALARM만 있고 통신·CCP 통합 알람 이력 테이블이 없음
- 결정: `TWIN_ALARM`(분류, 항목, 설비, 심각도, 메시지, 값, 상태 RAISED/ACKED/CLEARED, 시각 3종) 추가. TD5 테이블 기록은 그대로 병행
- 영향: 실제 MES 연동 시 매핑 필요

## D-007 장비 진단 지표는 트윈 내부 조회
- 맥락: 실제 PLC는 장비별 성공률·응답시간을 D영역에 내보내지 않음(spec 4.2는 상태·실패수·카운터만)
- 결정: 대시보드의 성공률·응답시간·오류유형·원시 프레임은 PLC/Edge 트윈 객체를 직접 조회. 상태 판정의 1차 근거는 D영역(+0, +1, +8)
- 영향: `live` 모드에서는 이 지표가 D영역 기반 값으로 축소됨

## D-008 DELAY 판정 기준
- 맥락: spec PLC-05의 "응답 > 주기의 80 %"는 타임아웃(300 ms)이 주기(5~10 s)보다 훨씬 짧아 발생 불가
- 결정: 최근 5회 평균 응답시간 > `delay_ms`(RTU 150 ms, TCP 250 ms, 설정 가능)이면 DELAY
- 영향: `sensor_delay(200)` 주입 시 DELAY로 표시되는지 테스트

## D-009 Edge 상태 보고는 내부 조회
- 맥락: metaprompt는 `POST /api/edge/status` 하트비트를 제안했으나 단일 프로세스(D-003)에서 불필요한 경로
- 결정: MES 토폴로지 서비스가 Edge 객체 상태를 직접 읽음. Edge–MES 링크 상태는 Sender의 마지막 전송 결과로 판단

## D-010 AC-02의 값 주소는 D0102
- 맥락: spec 14장 AC-02는 "D0100 값 ÷ 100"이라 적었지만, spec 4.2 블록 레이아웃에서 D0100은 통신 상태(+0)이고 염도 값은 +2(D0102)
- 결정: 4.2 레이아웃을 따르고 AC-02는 D0102로 검증
- 근거: 같은 문서 안의 구조 정의(4.2)가 예시(14장)보다 구체적

## D-011 Edge PLC 읽기 주기 500 ms
- 맥락: 금속검출 NG → 알람 2 s 이내(AC-07). PLC 스캔 1 s + Edge 읽기 1 s면 최악 2 s를 넘음
- 결정: `runtime.edge.plc_poll_ms` = 500. 두 PLC × 블록 묶음 읽기라 부하 영향 미미

## D-012 금속 NG 이벤트 주입 `metal_ng`
- 맥락: NG 확률이 0.2 %라 시험·시연 때 NG를 기다릴 수 없음. spec 8장 고장 목록에 이벤트 주입이 없음
- 결정: 순간 이벤트 유형 `metal_ng`(대상 MD-01)을 추가. 모델의 누적 검사·불합격 수를 1 올림 — 통신 경로는 그대로 탄다

## D-013 WebSocket 값 메시지는 장비 단위
- 맥락: spec 10.2 예시는 항목 1개 단위 메시지
- 결정: `{"type":"value","equip":…,"values":{항목:값}}` 장비 단위로 묶어 200 ms마다 합친다. 메시지 수가 1/2~1/4로 줄고 초당 5건 제한을 자연스럽게 지킴

## D-014 염도 항목에는 급변(max_step) 필터를 두지 않는다
- 맥락: 대시보드 점검 중 SAL-01 염도 9.0 %가 FILTERED로 버려지는 것을 발견. 센서 1식이 절임통 4기를 순환 측정해 목표 염도가 다른 통(12 %↔9 %)으로 바뀔 때 3 %p 넘게 뛰는 것은 정상 동작
- 결정: 염도는 물리 범위(0~30 %)만 검사. 회귀 테스트 `test_brine_tank_switch_not_filtered` 추가
- 영향: 실제 센서 노이즈 판정은 현장 데이터로 기준을 다시 잡는다

## D-015 토폴로지는 관측값만으로 판정한다
- 맥락: E2E 스모크에서, bus_cut 주입 직후 버스 노드가 장비보다 먼저 DOWN으로 표시되는 것을 발견. 토폴로지가 고장 주입 목록(정답)을 직접 읽고 있었음
- 결정: 버스·PLC·링크 상태는 Edge가 관측한 장비 상태로만 계산. 고장 목록은 시뮬레이션 화면에서만 보여준다
- 근거: 트윈 대시보드는 실장비(live 모드)에서도 같은 판정을 해야 한다

## D-016 React 19 사용
- 맥락: metaprompt는 React 18을 제시했으나 `npm create vite` 기본 템플릿이 React 19
- 결정: React 19 유지. 사용한 API(훅, react-router 7, zustand 5)는 18과 호환 범위

## D-017 MES DB 일일 정리 (매일 03:00)
- 맥락: 배포 서버에서 1.5시간에 mes.db 16.6 MB(하루 약 260 MB) 증가. 그대로 두면 디스크가 찬다
- 결정: 매일 `runtime.mes.purge.at`(KST, 기본 03:00)에 그 시각 이전 수집 데이터를 지우고 `VACUUM`으로 파일을 줄인다. `keep_hours`로 최근 N시간을 남길 수 있다(기본 0 = 전부 정리). 수집은 멈추지 않고 곧바로 다시 적재된다
- 남기는 것: 기준정보(BAS_EQUIP·BAS_CCP_STD·ORD_WORK_ORDER), 진행 중 절임 운영(SLT_TANK_OPR 절임중), 열린 가동 구간(EQP_RUN_LOG END_DT 없음), 해제되지 않은 알람, 남은 행이 참조하는 부모 행
- 이력: `TWIN_PURGE_LOG`(테이블별 삭제 수, 정리 전후 파일 크기). 수동 실행 `POST /api/admin/purge`, 대시보드 수집원장 화면의 "DB 일일 정리" 카드
- 주의: HACCP 증빙으로 수집 이력을 보관해야 하면 `keep_hours`를 늘리거나 정리 전에 외부로 내보내야 한다(v0.2 과제)
